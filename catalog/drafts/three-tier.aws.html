WEB APPLICATIONS

Classic three-tier web application
svg.awd
Amazon Route 53 and Amazon CloudFront with AWS WAF front an internet-facing Application Load Balancer, an Auto Scaling group of EC2 instances and an Amazon RDS Multi-AZ database across two Availability Zones. A request follows the numbered path and the response returns; the RDS primary replicates synchronously to the standby.
  1. Users look up the application domain name in Amazon Route 53.
  2. Amazon Route 53 answers with an alias record that points to the Amazon CloudFront distribution.
  3. Amazon CloudFront, with AWS WAF inspecting requests, forwards the request through the internet gateway to the Application Load Balancer.
  4. The Application Load Balancer routes the request to a healthy Amazon EC2 instance in the Auto Scaling group.
  5. The EC2 instance reads and writes data on the Amazon RDS primary DB instance.
  6. Amazon RDS replicates each write synchronously to the standby in Availability Zone b, and the response returns to users.
Three-tier web with a cache (cache-aside)
svg.awd
Amazon ElastiCache sits between the app tier and Amazon RDS. The first request is a cache hit and is answered from the cache; the second misses, so the instance reads RDS, populates the cache and returns the result.
  1. Users send requests to the Application Load Balancer in the public subnet.
  2. The Application Load Balancer forwards each request to the Amazon EC2 instance in the private subnet.
  3. The EC2 instance checks Amazon ElastiCache first. On a cache hit, it returns the cached result to users.
  4. The EC2 instance reads Amazon RDS on a cache miss, writes the result to ElastiCache and returns it to users.
Auto Scaling scale-out
svg.awd
The instances publish CPU to Amazon CloudWatch. When the alarm fires, Amazon EC2 Auto Scaling launches two more instances; once they are registered, the load balancer starts sending them traffic along with the original two.
  1. Amazon EC2 sends CPU utilization for the instances to Amazon CloudWatch, and the high CPU alarm goes into the ALARM state.
  2. The CloudWatch alarm triggers the scale-out policy in Amazon EC2 Auto Scaling.
  3. Amazon EC2 Auto Scaling launches two new instances into the Auto Scaling group.
  4. Amazon EC2 Auto Scaling registers the new instances with the load balancer, which sends traffic to all four once they pass health checks.
Availability Zone failure and failover
svg.awd
Traffic first spreads across both AZs. When Availability Zone a fails, the load balancer stops routing to it, all requests shift to the instances in AZ b, and Amazon RDS fails over so the standby in AZ b becomes the primary.
  1. Availability Zone a becomes unavailable, and the request in flight to it fails.
  2. The Application Load Balancer marks the targets in Availability Zone a unhealthy and stops routing requests to that zone.
  3. The Application Load Balancer sends all requests to the EC2 instances in Availability Zone b.
  4. Amazon RDS fails over: the standby in Availability Zone b becomes the primary, and the DB endpoint now resolves to it.
Outbound internet access with NAT gateways
svg.awd
Instances in the private subnets have no public address, so each AZ routes 0.0.0.0/0 to the NAT gateway in its own public subnet, which sends the traffic out through the internet gateway and returns the replies. Packets leave through AZ a first, then through AZ b.
  1. Amazon EC2 instances in each private subnet send internet-bound traffic through the 0.0.0.0/0 route to the NAT gateway in the same Availability Zone.
  2. The NAT gateway replaces the source address with its own and sends the traffic to the internet gateway.
  3. The internet gateway sends the traffic to the internet, and replies return through the same NAT gateway to the instance.
Containerized three-tier on Amazon ECS and AWS Fargate
svg.awd
An Application Load Balancer forwards requests to an Amazon ECS service whose AWS Fargate tasks use an Amazon Aurora cluster with a writer and a reader, and the tasks pull their image from Amazon ECR. The first request writes to the writer, the second reads from the reader.
  1. Users send requests to the Application Load Balancer in the public subnet.
  2. The Application Load Balancer forwards each request to an AWS Fargate task in the Amazon ECS service.
  3. The Fargate task sends writes to the Aurora writer and reads to the Aurora reader.
Blue/green deployment with weighted target groups
svg.awd
The Application Load Balancer forwards to two target groups, each backed by its own Auto Scaling group. The traffic weights move from blue 100% / green 0% to 50% / 50% and finally 0% / 100%, after which the blue path drains.
  1. Users send requests to the Application Load Balancer, which forwards them to two weighted target groups.
  2. The Application Load Balancer sends the blue target group (v1) its weighted share of requests: 100%, then 50%, then 0%.
  3. The Application Load Balancer shifts requests to the green target group (v2) as its weight rises to 50% and then 100%.
