VPC & HYBRID NETWORKING

Standard VPC across two AZs
svg.awd
A 10.0.0.0/16 VPC with a public and a private subnet in each of two Availability Zones. Inbound requests (orange) enter through the internet gateway and the load balancer to the private instances; outbound requests (blue) leave through the NAT gateway in the same AZ and then the internet gateway.
  1. Inbound requests from the internet enter the VPC through the internet gateway.
  2. The internet gateway delivers them to the Application Load Balancer, which has a node in the public subnet of each Availability Zone.
  3. The load balancer forwards each request to Amazon EC2 instances in the private subnets.
  4. The instances send outbound traffic by the private route table's default route to the NAT gateway in their own Availability Zone.
  5. The NAT gateway translates the private source address and sends the traffic by the public route table's default route to the internet gateway.
  6. The internet gateway sends the outbound traffic to the internet.
VPC peering
svg.awd
VPC A and VPC B are peered, and each route table sends the other VPC's CIDR to the peering connection, so requests (orange) and responses (blue) cross it privately. VPC C peers only with B, so traffic from A to C is not forwarded through B (red): peering is not transitive.
  1. An Amazon EC2 instance in VPC A sends traffic for 10.1.0.0/16, which its route table sends to peering connection pcx-1.
  2. The traffic crosses pcx-1 privately to the instance in VPC B, whose route for 10.0.0.0/16 returns the response over the same connection.
  3. VPC C peers only with VPC B, through pcx-2. VPC B does not forward traffic from VPC A to VPC C, because peering is not transitive.
VPC endpoints
svg.awd
A private subnet reaches AWS services without an internet gateway or NAT gateway. S3 and DynamoDB traffic follows route-table entries to gateway endpoints (orange); other services such as Amazon SQS are reached through an interface endpoint, a network interface powered by AWS PrivateLink (blue).
  1. Traffic from the Amazon EC2 instance to Amazon S3 or DynamoDB matches the service prefix lists in the subnet route table.
  2. The route table sends it to the gateway endpoints, which deliver it to Amazon S3 and Amazon DynamoDB without an internet gateway or NAT gateway.
  3. For other services, the instance sends traffic to an interface endpoint, a network interface with a private IP address in the subnet.
  4. AWS PrivateLink carries the traffic from the interface endpoint to Amazon SQS over the AWS network.
Transit Gateway hub and spoke
svg.awd
Three VPCs and an on-premises network attach to one AWS Transit Gateway, which routes between them with its route table. On-premises traffic (orange) crosses the Site-to-Site VPN to reach VPC B; VPC A reaches the shared services VPC C through the transit gateway (blue) with no VPC-to-VPC peering.
  1. On-premises servers send traffic from the customer gateway over IPsec tunnels to AWS Site-to-Site VPN.
  2. The VPN connection is attached to AWS Transit Gateway, which routes the traffic with its route table of propagated routes.
  3. The transit gateway sends the traffic through the Development VPC attachment, which has a subnet in each AZ, to the EC2 instances.
  4. An instance in the Production VPC sends traffic through its attachment to the transit gateway.
  5. The transit gateway routes it to the Shared services VPC, which runs AWS Managed Microsoft AD, with no peering between the VPCs.
Centralized inspection with Network Firewall
svg.awd
Spoke VPCs send traffic to the Transit Gateway, which hands it to an inspection VPC where an AWS Network Firewall endpoint in each AZ inspects it. East-west traffic (orange) is inspected and returned to the transit gateway for the other spoke; north-south traffic (blue) continues through a NAT gateway and the internet gateway.
  1. Spoke VPC A sends traffic by its default route through its attachment to AWS Transit Gateway.
  2. The transit gateway sends the traffic to the inspection VPC. Appliance mode keeps each flow in one AZ, where the AWS Network Firewall endpoint inspects it.
  3. The firewall returns allowed east-west traffic to the transit gateway, which delivers it to Spoke VPC B.
  4. Internet-bound traffic from Spoke VPC B also goes to the inspection VPC, here to the firewall endpoint in Availability Zone B.
  5. Inspected traffic leaves through the NAT gateway in the public subnet and the internet gateway to the internet.
Centralized egress
svg.awd
Spoke VPCs have no NAT gateways of their own: a default route sends internet-bound traffic to the Transit Gateway, which forwards it to an egress VPC with a NAT gateway in each AZ and one internet gateway. Outbound requests (orange) leave through the NAT gateways and responses (blue) return the same way.
  1. Instances in the spoke VPCs send internet-bound traffic by the default route through their attachments to AWS Transit Gateway.
  2. The transit gateway route table sends 0.0.0.0/0 to the egress VPC attachment, which has a TGW subnet in each Availability Zone.
  3. The TGW subnet route table sends the traffic to the NAT gateway in the same Availability Zone.
  4. The NAT gateway translates the source address and sends the traffic to the internet gateway. Its subnet routes 10.0.0.0/8 back to the transit gateway.
  5. The internet gateway sends the traffic to the internet. Responses return through the same NAT gateway and the transit gateway to the spoke.
Direct Connect with VPN backup
svg.awd
On-premises traffic normally takes AWS Direct Connect, through a transit VIF and a Direct Connect gateway to the Transit Gateway. When the Direct Connect location fails, BGP withdraws its routes and the traffic (requests orange, responses blue) fails over to the Site-to-Site VPN attached to the same transit gateway.
  1. On-premises servers send traffic from the customer gateway over AWS Direct Connect, the primary path.
  2. A transit VIF carries it to the Direct Connect gateway, which forwards it to AWS Transit Gateway and the Amazon EC2 instances in the VPC.
  3. When the Direct Connect location fails, BGP withdraws its routes and the traffic fails over to AWS Site-to-Site VPN on the same transit gateway.
Shared VPC with AWS RAM
svg.awd
A network account owns the VPC and shares two subnets with workload accounts through AWS Resource Access Manager (dashed). Each workload account then launches its own instances into a shared subnet (orange), and instances from both accounts talk over the VPC local route (blue).
  1. The network account shares two subnets of its VPC with workload accounts A and B through AWS Resource Access Manager.
  2. Each workload account launches its own Amazon EC2 instances into a shared subnet, while the network account keeps ownership of the VPC.
  3. Instances from both accounts communicate over the VPC local route for 10.0.0.0/16, with no peering needed.
AWS Client VPN
svg.awd
A remote client opens a TLS tunnel to the Client VPN endpoint (orange), which authenticates the user against an identity provider (blue) and then forwards traffic through a network interface in the associated subnet to private instances and databases.
  1. A remote client opens a TLS connection to the AWS Client VPN endpoint.
  2. The Client VPN endpoint authenticates the user through SAML federation with AWS IAM Identity Center.
  3. The endpoint forwards authorized traffic through its network interface in the associated subnet to the private Amazon EC2 instance and the Amazon RDS database.
AWS PrivateLink service
svg.awd
A provider exposes a service behind a Network Load Balancer as a VPC endpoint service. A consumer VPC in another account creates an interface endpoint, so requests (orange) reach the load balancer and its targets over the AWS network and responses (blue) return the same way, with no peering, internet gateway or NAT.
  1. An Amazon EC2 instance in the consumer VPC sends a request to the interface endpoint in its subnet.
  2. AWS PrivateLink carries the request over the AWS network to the provider's endpoint service in another account.
  3. The Network Load Balancer forwards the request to its EC2 targets, and the response returns the same way, with no peering, internet gateway or NAT.
